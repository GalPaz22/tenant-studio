# Tenant Studio — Core build pipeline

Run `npm start`, then open http://127.0.0.1:4320. `npm test` runs the verification suite.

The Studio now runs **Build store**: source inspection → complete connected-source crawl → normalization/specifications → taxonomy → store/domain research → product enrichment → evidence-based tags → product cards → store context → index → readiness checks.

## Execution and review

- Builds return a run ID immediately and execute outside the HTTP request. A local durable queue, raw page assets, per-product assets and checkpoints live under `data/runs/` (or `STUDIO_DATA_DIR/runs/`). At most two expensive operations execute concurrently in this single-server implementation.
- Pause, cancel and resume are available in the UI. Restarted running jobs become paused; queued jobs recover automatically. Completed work survives restarts. Failed stages can be retried without replacing the previous usable catalog.
- Source, model-call and elapsed-time budgets are enforced. A budget stop is paused, never successful completion. Budgets are counts/time, not a monetary price estimate.
- Imported products can be inspected before the build finishes and are explicitly marked as pending enrichment. Completed cards expose specifications, variants, tag decisions and source evidence.
- Every build pins a profile. Operator spelling/tag rules are preserved. Chat repairs use bounded category/product discovery and deterministic query inspection. They add scoped vocabulary links to selections of at most 200 existing product IDs, fix spelling, or edit existing aliases. Alias-only edits reuse cards, the index, and prior classifications; chat cannot create/change tag definitions or start a catalog rebuild. Deleted or changed definitions cannot silently reuse old assignments. Activated snapshots remain separate from draft chat edits.

## Catalog connectors

- Public WooCommerce Store API and Shopify JSON are crawled to exhaustion, without the legacy 500/10000-product ceiling. Pagination checkpoints, smaller-page restarts, repeated-page detection and duplicate-ID checks prevent silent truncation. Public-source coverage does **not** prove the complete store catalog.
- Authenticated WooCommerce REST v3 reads published products and all their variant pages; Shopify Admin GraphQL uses product cursors and exhausts variant connections. Server-side credentials are scoped to the configured store. Tokens are never stored in run assets or returned to the browser.
- Magento REST reads the product list/custom attributes, category tree, base currency, configurable-product children and salability for the configured inventory stock (default stock 1). Hidden/disabled child products remain hidden. Store-specific stock/store-code, media base URL and URL suffix can be configured; an unavailable inventory endpoint is an error rather than fabricated stock. This is coverage of the configured API/store/stock scope.
- JSON, CSV and TSV feeds are supported. JSON can be an array or `{products, nextUrl}` for paginated feeds. Product records require a stable `id`/`sku`, name, product URL, and available commercial/attribute fields. CSV variants/specifications can be JSON cells. A feed can be declared complete by the operator; that declaration is reported separately from measured source coverage.
- Nested same-origin XML sitemaps are crawled and Product JSON-LD is extracted. Failed pages remain incomplete. Server HTML is inspected; browser-rendered/JavaScript-only details are not claimed as collected.
- Before readiness, a second connected-source scan verifies product membership. Source additions/deletions or overlapping pagination block readiness and require a new import. A matching membership check is not a transactional snapshot guarantee for prices and stock; observations retain their timestamps.
- Each completed build is a source-scoped snapshot. Missing products disappear from the next active source view only after validation/activation. Older snapshots remain available; no failed/partial import deletes the active catalog or Mongo collection.

## Research, tags and context

- Public product pages supply descriptions/specification tables and attributed badges. Merchant price/stock conflicts prevent contradictory sale/stock badges from being displayed.
- Merchant-text extraction derives material, dimensions, capacity and other explicit attributes in batches. Every accepted value needs a literal quote from that product; invented evidence is rejected and conflicting values remain visible without overwriting the source specifications. This step can be disabled in build settings.
- Store homepage and discovered about/shipping/returns/terms links supply business context. Business facts/policies require a literal source quote; missing policies stay absent.
- Google Search grounding discovers sourced domain knowledge; returned claims, source links, queries and full research output are retained. Domain guidance is separate from exact product facts. See [Google grounding documentation](https://ai.google.dev/gemini-api/docs/generate-content/google-search).
- Optional per-model research discovers manufacturer sources. Explicit research URLs are also supported. External technical facts need an exact GTIN/MPN/model identity and literal nearby quotes. Model-prefix matches, invented values and merchant price/stock claims are rejected. Conflicting facts remain visible and never silently overwrite merchant specifications.
- Public sources discovered through grounded research share a 24-hour cache. Supplied feeds, authorized responses and private store data are not shared through that cache.
- Tags are classified in bounded groups of products/tags. Each pair keeps `matched`, `not_matched`, `unknown`, `conflict` or `failed`, its definition/product hashes and source quote. Positive/negative decisions need literal evidence. Model-memory knowledge cannot supply a verified assignment. Failed classification blocks build readiness; missing evidence remains unknown.
- Garmin-specific product rules live in a domain pack above the shared runner. The older Garmin research endpoint remains available for compatibility, but the main UI uses the generic build.

## Index and activation

- A persisted inverted index covers names, descriptions, specifications, categories/tags and exact identifiers. Preview reads this index and shares the same search service as the exported tenant runtime; cursor pagination is retained.
- Optional embeddings build a versioned 768-dimension vector index. Semantic candidate retrieval combines lexical and vector ranking, followed by source-evidence selection. The embedding model and content hash are pinned; incompatible vectors are not reused. Default: `gemini-embedding-2`, override with `STUDIO_EMBEDDING_MODEL`. See [embedding documentation](https://ai.google.dev/gemini-api/docs/embeddings).
- Choosing Mongo requires `MONGODB_URI`. Each build writes a separate staging collection, requests Atlas Search, waits for queryability and executes identifier smoke queries. Requested/pending/error is distinct from ready. Optional Atlas Vector Search is also created/tested. Mongo-ready builds use the Atlas text retriever; the local index remains available for local draft changes.
- Local activation selects one validated catalog/context/index snapshot. Active search is `/api/projects/:id/active/search`; ordinary `/search` is draft preview. Prior builds can be activated from the history panel. This is local version selection, not internet deployment or installation in a production store.
- ZIP export includes the actual shared runtime/dependencies, catalog snapshot, cards, evidence, tags, store context and build report, plus a widget with pagination and optional autocomplete. No live endpoint or tenant routing is published by export.

## Synchronization

The UI can enable periodic reconciliation (minimum 15 minutes) and optionally activate successful sync builds. It runs only while this local server is alive. Unchanged product enrichment is reused for up to 24 hours; tag decisions are reused only when product/definition hashes match. Changes are reprocessed; optional failures are reported. Automatic updates stop at the existing 100-revision limit.

`POST /api/projects/:id/sync/event` accepts `{eventId, productId, action: "create"|"update"|"delete"}` and deduplicates recent event IDs. A trusted local integration can use the Studio session token, or set `STUDIO_WEBHOOK_SECRET` and send `X-Studio-Timestamp` (Unix seconds) plus `X-Studio-Signature = HMAC-SHA256(secret, timestamp + "." + exact JSON body)` as hex. Signatures expire after five minutes. Events trigger reconciliation with incremental enrichment; they do not blindly delete products. Platform-native webhook/OAuth installation is not performed. The service stays loopback-only.

## Configuration and boundaries

The local `.env` supplies `GEMINI_API_KEY`/`GOOGLE_API_KEY`, optional `STUDIO_CHAT_MODEL` (chat defaults to Gemini 3.1 Flash Lite with minimal thinking), `STUDIO_MODEL` (build agent remains Flash), `STUDIO_RESEARCH_MODEL`, `STUDIO_AGENT_MODEL`/`STUDIO_JUDGE_MODEL` (studio agent and the reasoning reviewer that verifies its search fixes), `STUDIO_EMBEDDING_MODEL`, `MONGODB_URI`, `STUDIO_DATA_DIR`, `STUDIO_PORT`, and `STUDIO_WEBHOOK_SECRET`.

`STUDIO_CONNECTORS` is server-only JSON keyed by project UUID. Entries require the exact public store `host`:

```json
{
  "<woo-project-uuid>": {"host":"store.example","key":"<read-only key>","secret":"<secret>"},
  "<shopify-project-uuid>": {"host":"store.example","shop":"store.myshopify.com","token":"<read_products token>","apiVersion":"2026-07"},
  "<magento-project-uuid>": {"host":"store.example","token":"<read-only token>","stockId":1,"storeCode":"default","urlSuffix":".html"}
}
```

Credentials cannot redirect to another origin. All fetches validate/pin public DNS and reject internal networks. Responses default to 3 MB, feeds to 64 MB, with 15-second source timeouts. Remote content is information, never executable instructions. ZIP assets are compressed and bounded (256 MB per file / 512 MB total uncompressed).

This remains a local developer workbench with Host/Origin/session protection. It is not a multi-host worker system or an internet-facing authenticated admin service. Live tests of authenticated platform access, Atlas and optional embedding providers require their configured credentials; automated tests use injected providers to verify behavior without writing to external stores.

### Deleting a client

“מחק לקוח” (`POST /api/projects/:id/delete {name}`) requires retyping the client's name and is refused while one of its builds is queued or running. The project file, its build runs and agent log move to `data/trash/<id>-<time>/` (restore by moving them back into `data/`, `data/runs/`, `data/agent-logs/<id>.json`); the demo mirror cache is removed and a running site crawl is stopped. The client's own source database (Dashboard Mongo) is never touched.

### Stopping the agent

While the studio agent works (chat, “בדוק חיפושים”/“בדוק ותקן”, onboarding), the send button becomes **עצור**; the processing lab and scraper builder show their own “עצור” link. Stopping aborts the browser's stream; the server sees the disconnect and the in-flight model call is abandoned at once (its lock is released without waiting for it), and no further model/tool steps run. Agents save only on completion, so a stopped chat turn changes nothing; a stopped audit keeps the fixes already verified and saved as versions and skips the rest; a stopped onboarding starts no build. The agent log records the run as `stopped`.

### Tenant mini server for dashboard-server

**Connecting a URL-onboarded store to the dashboard** (“חיבור לדאשבורד”, `core/dashboard-connect.mjs`): creates the client in the schema onboarding-render writes — a `users.users` document (username, generated 64-hex `apiKey`, `dbName`, `platform`, `credentials.{dbName,categories,type,softCategories}`, `collections.products`, `onboardingComplete`, `syncMode:'studio'`, `createdBy:'tenant-studio'`) and `<dbName>.products` in the Woo/Shopify product shape with the studio's enrichment in `category`/`type`/`colors`/`description1`. It refuses an existing username or dbName and a non-empty products collection, writes products before the user, and leaves the production switch off. The project then behaves as an existing client (export, production switch, shopper analytics, crawler). Products carry no embeddings, so the store's search is its studio module. “סנכרן מוצרים למסד” re-sends the studio catalog (upsert by `id`) and only for stores the studio created.

“הורד מיני־שרת” (`GET /api/projects/:id/mini-server`, `mini-server.mjs`) packages one merchant's search as `tenants/<slug>/` in dashboard-server's tenant-module shape (the same contract as `tenants/garmin`: middleware for `POST /search` and `GET /search/load-more`, `<slug>-v3:` cursor tokens, 410 on expired cursors, 503 on failure), plus `tenants/semantix-registry.mjs`, which mounts every such folder. The folder holds the studio engine (only the files the search runtime imports; its one external dependency is `@google/genai`), the profile (rules, ranking, pipeline policy), and a snapshot of the enriched product cards. At request time the module reads the merchant's Mongo collection (cached for a minute) and overlays live price, stock, visibility, URL and image; products added since the snapshot are searchable unenriched and products removed from Mongo disappear. Result snapshots for paging live in `semantix_<slug>_sessions`. A tenant answers only for its `dbName` and only when its merchant user has `semantix: {module: "<slug>", enabled: true}`; otherwise the request falls through to the existing pipeline, which is the rollback. “ייצא לדאשבורד סרבר המקומי” (`POST /api/projects/:id/dashboard-export`) writes the module straight into the local checkout (`STUDIO_DASHBOARD_DIR`, default `~/Desktop/dashboard-server`): staged then swapped in, the previous version moved to `data/dashboard-backups/`, a folder the studio did not create (e.g. `tenants/garmin`) never overwritten, and a load check run with the server's own dependencies. Nothing is committed or pushed; `GET /api/dashboard` reports whether server.js is wired. The export writes code only: the module's data — the approved revision's profile plus the enriched cards, tags, store context and vectors — is published gzip-compressed to `semantix_module` in the merchant's own database (`<slug>:head` → parts of at most 8 MB; parts first, head last, previous edition kept). After export, every save that creates an approved revision republishes automatically (`core/module-publish.mjs`); the running module checks the head (one `_id` lookup) at most every 30 s, downloads an edition only when its digest changes, and keeps serving the edition in memory if a check fails. Engine code changes still need a re-export and deploy; profile, ranking, functions and catalog enrichment do not. A downloaded ZIP still carries `profile.json`/`snapshot.json`, used only while nothing is published. Install steps are in the package's `INSTALL.md`; the test suite loads the package against dashboard-server's own `node_modules` when `DASHBOARD_NODE_MODULES` is set.

### Shopper activity

The agent's `shopper_activity {days, limit}` (`core/shopper-activity.mjs`) answers "what do shoppers search / click / buy" for a time window from every signal the store logs: `queries` (searches the server logged), `product_clicks.search_query` and `cart.search_query` (clicks and add-to-cart from search, with distinct sessions), and `zero_searches` (hits, recoveries). It returns per-day counts per source and a `loggingGap` when searches stopped being logged while clicks continued, so partial data is named as such. It needs the project to be opened as an existing client (by username, name or dbName).

### Workspace context

Every agent turn starts with a WORKSPACE block (`core/workspace-context.mjs`): the merchant's production settings from the dashboard user document (store description, concierge, out-of-stock display, categories, the Semantix module switch — never email, API key or credentials), this week's shopper activity (top searches with click/cart sessions, zero-result searches, logging gaps), the current setup (pipeline, ranking rules, functions, linked terms), the last five versions, the comparison with production, the exported module and the operator's earlier requests. Live parts are stored on the project and refreshed at most every 6 hours; a failed read only leaves them out.

Model replies: a key that lost its opening quote is repaired locally, a list of replies is merged, and function calling is disabled (`toolConfig: NONE`) so a model that sees the tool list in the prompt cannot answer with an empty native call.

### Agent cost

The studio agent's prompt starts with a part that is identical for every tenant and every round — role, engine notes, playbook, tool list (~5.6K tokens) — followed by the merchant, conversation, request and tool results. That static part is stored once per model in an explicit Gemini context cache (1-hour TTL, renewed while used) and each call sends only the rest; if a cache cannot be created or is rejected, the whole prompt is sent as before. Tool results older than two rounds are cut to a 300-character excerpt, and only the latest verification verdict and state digest are kept; the conversation sent is the last 8 messages (the last two in full). Token usage per model call is recorded in the agent log (`promptTokenCount`, `cachedContentTokenCount`).

### Agent model and stock policy

The studio agent runs on `gemini-3.8-flash` (`STUDIO_AGENT_MODEL` overrides it, e.g. `gemini-3.1-pro-preview` for deeper, slower turns); the reviewer and planner run on Pro. Up to 36 model rounds per request, 3-minute calls. `pipeline.outOfStock` (set by the agent through `configure_search`) decides what shoppers see: `hide` (default) only in-stock products; `last` also out-of-stock products after all in-stock ones; `show` out-of-stock products in their natural place. Hidden products are never shown. Every engine path (index, lexical scan, spelling, LLM, alternatives), the reviewer and the exported mini server follow the same policy.

### Tenant functions (custom code per merchant)

The studio agent can write the merchant's own JavaScript (`write_function`, `test_function`, `remove_function`; `core/tenant-hooks.mjs`): `rewriteQuery(query, ctx)` before retrieval, `transformProduct(product, ctx)` once per product when the catalog loads (adds tags, categories, specifications, description, popularity, brand — title, image, id, url, price, stock and visibility always stay as in the source), and `rerank(matches, query, ctx)` for the final order (after ranking rules; ids left out are dropped). `ctx` holds `data` (the tenant's own JSON, ≤200KB), `normalize` and `words`. The code is stored in the profile, so it is versioned, reversible, verified like any rule, shown for review under “גרסאות וכללים”, and travels in the exported mini server. Before saving, a function runs on the whole catalog (or sample queries) and any error rejects it.

Isolation, in layers: the source is rejected if it names escape routes (`this`, `import`, `require`, `process`, `eval`, `Function`, `constructor`, `async`, timers, network…); it runs in a worker thread with a 64MB heap, inside an empty VM context that cannot compile strings; data crosses only as JSON text; each call has a time limit (100 ms per search call, 8 s for the catalog). A failing, slow or crashing function is reported in `metadata.functionErrors` and the search continues without it. This is defence in depth for model-written code, not a hard security boundary between tenants — review functions before switching a module on in production.

### Production control of tenant modules

A module in dashboard-server answers only when the merchant's user document switches it on: `users.users → semantix: {module: "<slug>", enabled: true, percent: 100}`. dashboard-server copies the field into `req.store.semantix` (store config, cached up to 5 minutes); `tenants/semantix-registry.mjs` serves the module when the field names this module, is enabled, and the store's dbName is the module's dbName. `percent` sends that share of shoppers (stable per session id). Activation and deactivation use the Studio controls; no environment switch is required. A failed new search falls through to the existing pipeline, and 5 failures within a minute pause the module for 5 minutes. `GET /semantix/status` (header `X-Semantix-Admin: $SEMANTIX_ADMIN_TOKEN`) lists loaded modules, the users that switch them on, circuit state and counters; module responses carry `X-Semantix-Tenant: slug@revision`. The studio's “שליטה בפרודקשן” panel reads and writes the field on the merchant's user (found by username, else by the store's dbName; `STUDIO_DASHBOARD_MONGODB_URI` or `MONGODB_URI`), after confirmation; switching on requires an export. If a hand-written tenant folder already has the module's name (e.g. `tenants/garmin`), the module is exported as `<slug>-semantix`.

### Search speed and LLM use

`pipeline.expansion` sets whether a short query that already has literal matches also waits for LLM expansion: `always` (default, broadest, typically 3-15 s), `sparse` (only when literal matches are fewer than `pipeline.expandBelow`, default 8) or `off` (index only, milliseconds). Complex queries and queries without literal matches still use the LLM. The agent changes it with `configure_search` (partial settings), measures real latency per query with `measure_search` (phase, llmUsed, elapsedMs), and reads the engine's own code read-only with `read_engine` before explaining behaviour. The reviewer judges the current request (earlier requests only resolve references), and sees each query's phase and timing.

### Ranking rules and catalog structure

The studio agent can change result ORDER, not only which products match. A ranking rule (`profile.rankingRules`, agent tool `rank_rule`) boosts or buries a product group defined by catalog structure — exact category/tag/product-type labels, or a brand/specification value — optionally only for queries containing given words. Rules act on the final result list of every search path (lexical, spelling, router, LLM, alternatives) and inside relevance tiers: a product whose own title names every query word always stays above one that does not, and with the default `match: "direct"` only group products that name the query move. So "ירקות ופירות קודם" lifts fresh tomatoes for "עגבניות" while "רוטב עגבניות" keeps the sauces first. Results report `metadata.ranking`; the production baseline and the exported module apply the same rules. `tag_products` adds (or removes) a tag on a whole product group when no field separates a kind of product; tags are searchable and usable by ranking rules.

Hebrew singular and plural of a query word match each other in the local index when the other form exists in the catalog (בננות↔בננה, עגבניות↔עגבניה/עגבנייה, תפוחים↔תפוח, מלפפונים↔מלפפון, final letters handled); the exact form ranks first. Fuzzy matching is unchanged.

The agent's playbook first classifies a request: a question is answered without changing rules; an ordering request uses `rank_rule`, never per-query pinning; examples given by the operator are treated as a class, solved with one structural rule and verified on examples plus a neighbouring query that must not change. The reviewer judges order for ordering requests. A tool call that already failed, or a change that is already applied with nothing changed since, is refused instead of being repeated; a failed verification leads with what was not saved, and the agent's own claims are shown below it as unverified.

### Focused search repair

The chat agent has up to six tool rounds to inspect categories, select products by exact category and title substring, and inspect deterministic query results. A scoped alias augments existing literal matches; it never labels product facts. The response records tools used, selected-product count, and before/after query results. Product selections are snapshots of existing IDs; future products are not implicitly added. No catalog source reads, classification jobs, or index rebuilds are started by chat. The former automatic `/repair` rebuild endpoint is disabled; explicit build controls remain separate.

Complex search (four or more words, or explicit negation) bypasses cheap lexical/router shortcuts and uses `STUDIO_SEARCH_MODEL` (default `gemini-3.1-flash-lite`, medium thinking) for both interpretation and evidence-based selection. Chat repair uses Gemini 3.1 Flash Lite. The studio agent's answer is not final until a fresh search passes review: the harness reruns the real search for the operator's quoted queries, a separate reviewer judges each returned product by id against the request, and a failed verdict (named unwanted or missing products) sends the agent back to fix it, up to three rounds; an unverified fix is reported as such. “בדוק חיפושים” / “בדוק ותקן” (`POST /api/projects/:id/audit {fix}`) reviews real shopper queries from the client database — zero-result searches (`queries.deliveredProducts`), searched-but-never-clicked (`product_clicks`/`cart`, same time window) and the most searched — against the current rules. With fix, up to five findings go to the studio agent one query at a time; only fixes that pass their own verification are saved (each as a version, plus a pending regression example), and earlier fixes are rechecked after later ones. Open findings are passed to the studio agent as `lastAudit`. Linked terms can add products (`mode: "add"`) or narrow a word to exactly the linked products (`mode: "only"`, e.g. "יומן" → diaries rather than novels titled "יומן"). Semantic matches require evidence for every constraint, including specifications. When full matching fails, a bounded model pass ranks closest alternatives and reports missing constraints. If the provider fails, local similarity returns explicitly unverified suggestions. Only visible in-stock tenant products are eligible; an empty eligible catalog remains empty. Search examines a bounded candidate set and does not reclassify the catalog.

### Focused learning trial

The learning panel imports existing repair checks and scoped rules as **unconfirmed** examples. Review expected and unwanted products, then confirm examples. A bounded Flash model call proposes up to six equivalent search phrasings; each proposal previews a scoped alias against the existing cards/index and checks confirmed examples. Applying requires explicit review, a confirmed source example, a fresh profile/catalog check, improvement, and passing confirmed examples. Later chat repairs that break previously passing examples are rejected.

These are deterministic retrieval checks, not proof of semantic equivalence or end-to-end LLM ranking quality. No model training, catalog classification, or automatic application occurs. Approved rules travel with the exported profile; confirmed examples are included in `learning-tests.json` as data (no automatic test runner). Suggestions remain reviewable hypotheses.

### Existing Dashboard clients

Use “עבודה על לקוח קיים” and an exact username to open saved MongoDB products, categories and tags. The connection uses `STUDIO_DASHBOARD_MONGODB_URI`, falling back to `MONGODB_URI`; the username is resolved through `users.users` and the stored `dbName`/`collections.products` mapping. This reads existing data only, creates a local working snapshot and local search index, and does not crawl, classify, or write to the source database. Reopening returns the existing local project, preserving edits. Imported tags are displayed as stored labels; this does not import the production search code or infer tag definitions. The current limit is 50,000 products, with an explicit error rather than silent truncation.

### Existing-client fast track

The existing-client panel can analyze saved context plus recent query signals and separately rebuild the local index from the current cards. It never starts catalog sync, scraping, classification or activation. Analysis aggregates all cards, sends up to 80 distributed product examples, the profile/context, and top query aggregates to the configured chat model. Mongo reads are limited to the latest 10,000 events per source. A missing result count is unknown, not failure; attributed add-to-cart events are labelled as such, not purchase conversions. Recommendations are proposals only; reindexing does not apply proposed translations or other enrichment. The report and index stay in the local project and travel with the existing snapshot export where applicable.

### Workspace chat agent

The chat uses `/agent` for projects with saved cards. Its context includes catalog-wide summaries, sampled products, profile, saved fast-track report and conversation history; paginated tools inspect products and distinct field values across the saved catalog. Tools can refresh query aggregates, apply focused search repair, adjust bounded candidate/router settings, reindex, and derive a new searchable specifications field from an existing text field. Processing deduplicates source strings, runs batches of 40 up to 1,000 distinct values per operation, preserves source fields and records model-derived provenance. “Undo processing” removes the most recent derived field. Unsupported/missing source fields require clarification; the agent cannot change arbitrary code, crawl, or deploy. Changes are staged in a copy and saved only on successful completion with non-regression of confirmed examples. New fields invalidate vector snapshots and are indexed locally; they are not independently source-verified facts.

## Per-tenant search loop

The studio's goal for an existing client is to replace its current search: keep everything that works and deliver where it fails.

- **Baseline against production** ("מול הקיים"): built from the client's own logs (`queries`, `product_clicks`, `cart`, default 30 days). A query *works* in production when shoppers repeatedly chose products (clicked ≥3 with a real share, or carted); those products are the keep targets. It *fails* when it mostly returned nothing or was never clicked. Chosen products missing from the catalog or out of stock are reported as catalog gaps (the site crawler closes them), not as search failures. Evaluation is deterministic (local index): kept / partial / lost / gap, weighted by searches.
- **Regression guard**: every studio-agent save is checked against the queries currently kept; a change that loses one is sent back to the agent once, then refused.
- **Fixes from real queries**: "תקן אבודים" (`POST /audit {fix:true, source:"baseline"}`) sends the most-searched lost queries to the agent with the products shoppers chose; a fix is kept only when it passes the reviewer and those products come back.
- **Processing lab** ("עיבוד"): `STUDIO_PLANNER_MODEL` (default `gemini-3.1-pro-preview`) researches the tenant with a playbook of standard e-commerce search processing (field completion, cross-language bridging, spelling normalization, taxonomy and attributes, evidence-based tagging, doc2query expansion, dense embeddings, identifiers, offline measurement) and proposes up to six plans, each citing the queries it should fix: `import_db_field`, `derive_field` (translation / transliteration / normalization over distinct values), `extract_pattern`, `enrich_products` (per-product grounded field, e.g. shopper keywords), `classify_tag` (evidence-quoted classification; the label becomes a searchable tag), `embeddings` (256-d `gemini-embedding-2` vectors stored compactly as `studioVectors` and used by the semantic candidate stage), or an `idea` that needs implementation (shown, not run). Plans are tried on a sample with a cost estimate, run with `STUDIO_PROCESSING_MODEL` (default `gemini-3.8-flash`), measured against the baseline (embeddings: sampled full-search check) and rolled back automatically if they lose a kept query; every run can be undone.
- **Dedicated scraper** ("סורק" → "סורק ייעודי ללקוח"): the planner writes a declarative product-page spec (product URL rule with key, JSON-LD paths or CSS selectors per field) from sample pages; it is validated on more pages and against the catalog, refined once if weak, and used by the tenant's crawl after the operator activates it.
- Models: the studio agent defaults to `gemini-3.8-flash` (`STUDIO_AGENT_MODEL`); the reviewer (`STUDIO_JUDGE_MODEL`) and planner default to Pro.

### New client from a URL

“לקוח חדש מכתובת אתר” (`POST /api/onboard {url}`, NDJSON progress) onboards a store for a demo from its address alone (`core/onboard.mjs`):

- **Detect.** The homepage is read (canonical host adopted from `<link rel=canonical>`/`og:url` or the sitemap, so `shop.co.il` → `www.shop.co.il` works), platform signals are noted, and the public catalogs are *probed*: Shopify `/products.json`, WooCommerce Store API. A working one is read to exhaustion (`sourceType: platform`).
- **Otherwise pages.** robots.txt `Sitemap:` entries, `/sitemap_index.xml`, `/sitemap.xml` are tried; product sitemaps are preferred (`sitemapFilter`). Without a usable sitemap the store's own links are followed from the homepage (`sourceType: crawl`: same-origin, robots.txt obeyed, queries dropped except pagination, bounded frontier, polite pacing). Sampled pages decide the extractor: structured data (any Product/ProductGroup or a named item with offers, e.g. `Book`) is used directly; markup-only pages get a **dedicated scraper** written by the planner model from the samples, validated on them and activated automatically only if names and product keys were extracted on ≥80% of pages.
- **Build.** A demo build is queued: full catalog → store/domain research → evidence tags → cards → store context → local index. Page-based sources skip the second full read of the source (reported as `membershipVerified: skipped`). An onboarding build that ends `partial` (e.g. some tag batches failed) is still adopted as a draft revision so the demo works; its gaps are listed in the chat. Budget stops pause the build; “המשך בנייה” resumes it with doubled limits.
- A host that is already a project reopens that project. Sites that render products only in the browser or block the server are reported with a request for a feed/API instead.

### Demo on the client's own site

“הדגמה על האתר” opens `/demo/:id/`: a live mirror of the tenant's storefront served through the studio, with its own search answered by semantix (draft revision).

**Native search (default).** The site's own autocomplete and results page run unchanged; the mirror intercepts search responses (`q`/`s`/`query`… on search/suggest/autocomplete paths, HTML or JSON) and replaces only the product-card region. Cards are found by product links matching the catalog; the list is the largest repeating group, and its shape is learned per endpoint (probing the site with a product title when the original is too sparse). Each semantix result's card is harvested from the same endpoint by searching its SKU/URL key, so price, stock, author and badges are the site's live values; a product the site cannot surface is transplanted into another card with its price blanked. Result counts ("54 פריטים", "נמצאו 79 תוצאות") become the semantix total; unrelated numbers (mini-cart, menus) are kept. When the original has no results, the structure comes from a harvested page with the query text restored. `?p=`/`?page=` pages through semantix results. Harvesting is polite: every card seen on an endpoint is reused, requests are capped at 12/min per site (the rest are transplanted), and responses without product cards (articles, suggestion-only sections) are skipped. A bot-protection page (Cloudflare/Shopify challenge) is never cached; it pauses harvesting for that site for 10 minutes and the demo shows an explanatory page instead. The mirror does not attempt to bypass such checks — ask the client to allow the server's IP if needed. Sites whose search is rendered client-side by a third-party service are not intercepted; `?__semantix_mode=overlay` switches that demo to a separate results panel (`native` switches back). Pages, CSS, JS and images come from the store itself; same-store URLs are rewritten to stay under `/demo/:id`, root-relative requests built at runtime are redirected there by Referer, and CSP/frame/SRI blockers are removed. The site's search inputs, forms and `?s=`/`?q=` result URLs open the semantix overlay; product links stay inside the mirror. Project listing and background ticks read small `<id>.meta.json` sidecars (rebuilt when the project file's mtime changes), never full project files. Only the project's host (±`www.`) is proxied — this is not an open proxy. The mirror is read-only: non-GET requests (cart, login, analytics beacons) are refused, cookies are not passed in either direction, and service workers are disabled. Fetched responses are cached under `data/mirror/<id>/` so a demo keeps working if the site changes or is slow; add `?__semantix_refresh` to a URL to refetch it. Pages are marked `noindex`. Sites behind bot protection (e.g. Cloudflare challenges) may not load.

### Storefront plugin packages

“גרסאות וכללים” → “יצירת פלאגין לאתר” generates a platform-specific ZIP (`POST /api/projects/:id/storefront-plugin`) from the selected platform, HTTPS search endpoint, CDN base URL and optional **public search-only** storefront key. WooCommerce gets a WordPress plugin folder, Shopify a theme app embed to integrate into an existing Shopify app, Magento 2 a module with layout/CSP configuration, and Custom an embed snippet. The common integration captures the store's existing search forms, replaces the product grid with Semantix results, and clones an existing theme product card so the result markup retains the store's CSS classes. It falls back to a minimal card when no theme card can be discovered. It does not sync inventory.

The package includes content-hashed JavaScript, a Cloudflare Workers Static Assets configuration, and installation/rollback instructions. Other static hosts can serve the same assets. Deploy the search backend separately and configure tenant authentication, CORS and rate limits there. All CDN code/configuration is public; never enter Studio/admin/provider secrets. Generation neither publishes assets nor installs the package into a store. Shopify still requires app deployment and merchant app-embed activation. Browser/API tests run with `node --test storefront-plugin.test.mjs storefront-plugin-api.test.mjs`.

### Customer questions and conversion-led search repair

The Studio agent's `customer_analytics` tool reads only the connected merchant's database: `queries`, `product_clicks`, `product_click_events`, `cart`, `add_to_cart_events`, and `checkout_events`. It supports explicit half-open date ranges or 1–90 days, exact query drilldown, and rankings by searches, clicks, carts, purchases, or lowest purchase conversion (default minimum 20 distinct search sessions). It returns recorded order totals separately by currency and product evidence matched to the local catalog. Customer identities, contact details and raw session IDs are not returned to the agent.

Purchase conversion is distinct searched sessions with a later attributed purchase divided by distinct searched sessions for the query. Explicit search-query attribution and inferred last-search attribution (same session, within 24 hours) are reported separately. Known unpaid/cancelled/refunded statuses and checkout initiation are excluded; order IDs deduplicate purchase retries. Missing sessions or no matched search/purchase evidence means unknown conversion. Missing or truncated sources disable conversion rates; reads are bounded at 50,000 records per source and failures are reported, not silently converted to zero.

For “תקן את השאילתות הכי פחות ממירות”, the agent first reads fresh analytics, drills into candidates, checks clicks, search results and catalog availability, then applies supported search repairs with existing verification/regression safeguards. Low conversion alone is not proof of poor relevance; an offline search repair is not evidence of increased sales. Customer questions are read-only unless a change was requested. Existing store context/catalog/settings tools answer other merchant questions. This does not add missing storefront tracking or deploy local repairs to production.

### Shared client profile and search performance review

The client profile (`core/client-brain.mjs`) resolves platform identity from the connected dashboard user and project/onboarding evidence. A specific dashboard platform replaces legacy imported `custom` placeholders; contradictory specific platforms remain unresolved. Plugin generation reads this profile server-side and ignores a browser-supplied platform. The Studio displays the resolved platform rather than a manual selector. Successful refresh keeps the project's platform aligned for existing consumers.

“בקרת חיפוש” runs `POST /api/projects/:id/performance/review` for a 7/30/90-day window using the configured Pro planner with reasoning (`plannerModel()`). It collects fresh tenant analytics, catalog and configuration evidence, baseline summaries, and up to six actual local draft searches. Reports retain the model, timestamp, revision, data limitations, sample timings, and up to six proposed actions spanning ranking/pinning, processing, indexes, functions, pipeline, catalog and tracking. Timing is a small local sample, not production telemetry. Reports and the last four previous reports persist on the project; the agent can read or refresh them with `search_performance`. Processing research also consumes the report.

Each proposal includes evidence, affected queries, hypothesized impact, risk, success metric and validation/rollback instructions. “העבר לאייג׳נט לבדיקה וביצוע” prepares an explicit chat request; it does not execute model-generated code or publish changes. Changed catalog/profile fingerprints block stale proposals. Unsupported ideas (including a new index architecture or native pinning) are implementation work, not falsely marked as completed. This is on-demand monitoring; no background schedule or automatic production tuning is enabled.
